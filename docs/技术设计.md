### 2.2 我们的接缝

`agent/request-error` 是**可返回决策**的 waterfall：

```ts
// packages/core/agent/src/runtime-types.ts:353
'agent/request-error'(this: Scoped<Agent>, payload: {
  agent: Agent; turn: number; step: number; provider: string
  failure: LlmFailure; retryPolicy: ResolvedRetryPolicy | undefined; signal: AbortSignal
}, next: () => Promise<RequestErrorAction>): Promise<RequestErrorAction>

// runtime-types.ts:122 —— 唯一的非空决策
export type RequestErrorAction = { kind: 'retry' } | undefined
```

- 事件自 `v0.1.1-rc.2` 起即为 waterfall（`knowledge/v0.1.7-rc.2/api-reference/20-events-index.md:45`），本代无变化。
- `failure` 结构经校验，只允许 `message / code / status / providerRetryAfterMs / requestId / offloadImages`（`packages/llm/llm/src/types.ts:41-58`）。本插件的 `failure` **原样透传 payload**，不改写、不添加自定义字段。
- 调用方在 waterfall 之后 `signal.throwIfAborted()`（`agent.ts:488`）⇒ 中止语义由平台负责，插件只需正确响应 `signal`。

### 2.3 平面归属

**Host 平面 / bundle 行**（`must-read/03` §1 判据：跨会话、进程级、与 `dsh-llm-retry` 同类）。不是 preset 行——它不是「某个 agent 看到的工具/提示/策略」。

## 3. 判据

三层与，全部满足才介入：

1. `provider ∈ config.providers`（默认 `["openai-codex"]`：三句均为该上游的文案，避免波及其它 provider）。
2. `failure.code === "PI_AI_ERROR"`（已进白名单的码由平台处理，本插件不介入以避免双重重试）。
3. `failure.message` 命中三条正则之一：

```js
const TRANSIENT = [
  /Our servers are currently overloaded\. Please try again later\./i,
  /An error occurred while processing your request\b[\s\S]*you can retry your request/i,
  /exceeded request buffer limit while retrying upstream/i,
]
```

第 3 条与上游 `dsh-codex-subscription@2.6.8` 的改写**正向重叠且无冲突**：升级后该文本被改写成 `Network transport failure: exceeded request buffer limit …`，被 `classifyPiAiError` 归为 `TRANSPORT` → 由平台默认策略重试（maxRetries 5）→ 本插件**不会被调用**。我方正则仍能匹配原始子串，属安全冗余。

## 4. 事件链算法（不变量合规的关键）`[读码]`

`retry` 序号与 `retryId` **从会话日志推导**，与校验器使用同一算法（`invariant.ts:106-118`），因此不可能与校验器不一致；无需注册 session projection。

```js
const POLICY_KEY = 'llm-transient-retry-v1'

ctx.on('agent/request-error', async (payload, next) => {
  const { agent, turn, step, provider, failure, signal } = payload
  if (!config.providers.includes(provider)) return next()
  if (failure?.code !== 'PI_AI_ERROR') return next()
  if (!TRANSIENT.some(re => re.test(failure.message ?? ''))) return next()

  const history = agent.session.snapshotEvents()
  const prior = lastOf(history, e => e.type === 'llm/retry'
    && e.data.turn === turn && e.data.step === step
    && e.data.provider === provider && e.data.policyKey === POLICY_KEY)
  const retry = (prior?.data.retry ?? 0) + 1
  if (retry > config.maxRetries) return next()          // 用尽 → 交给原错误继续 throw

  const retryId = prior?.data.retryId ?? randomUUID()   // 同链必须复用（不变量 116-118）
  const delayMs = backoff(retry)                        // 1.5s → 3s → 6s，cap 30s，±30% 抖动

  agent.session.append('llm/retry', {
    retryId, turn, step, provider, mode: 'normal', policyKey: POLICY_KEY,
    retry, maxRetries: config.maxRetries, delayMs, failure,
  })
  if (!await cancellableDelay(delayMs, AbortSignal.any([signal, lifetime.signal]))) return
  agent.session.append('llm/retry-started', { retryId, turn, step, retry })
  return { kind: 'retry' }
})
```

顺序与 `dsh-llm-retry` 一致：**先写 `llm/retry` → 可中止等待 → 写 `llm/retry-started` → 返回决策**（`llm-retry/src/index.ts:188-191`）。中止时返回 `undefined`（与 `llm-retry` 同语义，平台的 `throwIfAborted()` 接管）。

## 5. 不变量对齐表

`llm/retry` 的事件**不是自由格式**：`packages/llm/llm-retry/src/invariant.ts` 逐条校验，`fail` 的实现是 **throw**（`packages/runtime-diagnostics/invariants/src/index.ts:161` → `InvariantError`），且挂在新事件派发（`invariant.ts:162-169`）与装机复核（`:159-161`）两侧。⇒ 写出不合规的事件会**当场抛**，且已落盘的历史会污染后续复核路径。

| 不变量条款（`invariant.ts` 行号） | 本算法为何满足 |
| --- | --- |
| `retryId` 非空字符串（51-53） | UUID |
| `failure` 完整（19-42） | 原样透传 payload，不做改写 |
| `retry` ≥ 1 且为安全整数（56-58） | 由 prior + 1 推导 |
| `provider` 非空（59-61） | 取 payload |
| `policyKey` 非空（62-64） | 常量 `llm-transient-retry-v1` |
| `mode:"normal"` 需 `maxRetries ≥ 1` 且 `retry ≤ maxRetries`（66-71） | 超出即 `next()`，不写事件 |
| `delayMs` ∈ `[0, 2147483647]`（79-82） | 上限 30s（`packages/util/timeout/src/index.ts:25`） |
| 必须在 open turn 内且 turn 一致（84-91） | 失败发生在该 turn 的请求内；用 payload 值 |
| 必须在 open step 内且 turn/step 一致（93-100） | 同上 |
| `provider` 必须等于 open step 的 provider（101-104） | 用 payload 的 provider（与 `llm-retry` 同源） |
| `retry` = 同 (turn,step,provider,policyKey) 链前值 + 1（106-115） | 与校验器同一算法 |
| 同链必须复用 `retryId`（116-118） | 复用 prior 值 |
| 新链不得撞用他人 `retryId`（119-123） | 新链用新 UUID |
| `llm/retry-started` 必须配对且不重复（127-146） | 严格按算法顺序各写一次 |

**已知缺口**：`ctx.on('agent/request-error')` 的监听器**无法**通过上游真不变量校验器自测——校验器只认 `ctx.sessions` 里的真实会话事件。故测试策略见 §9。

## 6. GUI 契约（不需要 client 半侧代码）`[读码]`

`packages/client/ui-chat/src/client/conversation-nodes/retry.ts`：

- `match`（44-55）：按 `retryId` 聚链，`retry === 1` 记为 `start`，其余 `update`。
- `start/update`（56-73）：node 由 `...event.data` 展开，`llm/retry-started` 把同 `retry` 的 attempt 标为 `started`。
- `buildViewNode`（74-88）：turn/step 关闭时，仍处 `scheduled` 的最后一次 attempt 显示为 `cancelled`。

⇒ 推论：**每条重试新生成 `retryId` 会在 GUI 上渲染成一叠独立卡片**，而按链复用 `retryId` 才是一条带多次 attempt 的链。GUI 诉求（55-73）与不变量诉求（`invariant.ts:116-118`）在此完全一致。

## 8. 包结构

```text
dsh-llm-transient-retry/
├── package.json          # name/type/main/exports/files/dsh.bundle + peer(见下)
├── cordis.patch.yml      # 一行：{ id: llm-transient-retry, name: dsh-llm-transient-retry }
├── src/
│   ├── core/             # 纯领域逻辑（禁 @deepseek-ai/*）：判据正则、退避序列、链序号推导
│   └── adapter/          # apply(ctx, config)：ctx.on 接线、session.append、effect 清理
├── test/                 # node:test：core 单测 + adapter 接线 + 上游真校验器 + 真 Loader 组合（见 §9）
└── docs/
```

要点：

- **无构建步骤**（无 client 半侧）⇒ `files` 只列 `src/` + `cordis.patch.yml` + `README.md`；⇒ `github:` 安装**不会**触发 pnpm 的 `prepare` 授权坎（`must-read/05` §5）。
- 插件形态取具名导出（`export const name` / `Config` / `export function apply`），与 `must-read/03` §2 的「函数式（最常见）」及 `@deepseek-ai/dsh-llm-retry` 自身一致；不用 default 对象形态，避免与具名导出混用。
- 实际依赖面：`dependencies` 只有 `@deepseek-ai/schemastery`；**不声明任何 `peerDependencies`**（本插件不消费 DSH 服务），因此不受 peer 版本门禁的静默禁用影响。
- 依赖分类按 `must-read/04` §7 的规则是：消费 Service Definition 的 `@deepseek-ai/dsh-*` 走 `peerDependencies`；`@deepseek-ai/schemastery` 可放 `dependencies`。本插件**不消费任何 DSH 服务**——只用框架继承的 `ctx.on` / `ctx.effect` 与 `agent.session.append`，不 import 任何 `@deepseek-ai/dsh-*`，故整条 peer 面为空是**结论而非漏声明**：它不落在那条分类规则里，也就不会触发 peer 版本门禁。
- ⚠️ 本仓库外无法使用 `workspace:*` 协议（那是 DSH monorepo 内部约束）。范围写成 `^0.1.7-rc.2` 形态；须记住 peer 门禁的判定带 `includePrerelease: true`（`must-read/05` §7.2.1），不带该选项的离线复核会**整列判错**。
- 测试依赖**必须钉精确版本**：`@deepseek-ai/dsh-*` 内部包的 npm `latest` dist-tag 停留在过期的 `0.0.1-rc.1`，装 `latest` 会拿到错误代际。
- 组合测试只需再加 `@deepseek-ai/cordis-plugin-loader` 与 `-include`；这两个包走**自己的版本线**（运行时用 `1.0.5` / `1.0.9`），**没有** `0.1.7-rc.2` 这个版本，按 DSH 版本号去装会 `ERR_PNPM_NO_MATCHING_VERSION`。`@deepseek-ai/cordis` 同理（运行时 `4.0.4`）。版本口径以 `versions/<版本>/node_modules/.pnpm` 现查为准。

### 9.2 激活证据（2026-10-14，`[实测]` 于运行中的 test 实例）

通道：`knowledge/v0.1.7-rc.2/client/17-remote-rpc.md` §7 的无浏览器只读取证——`GET /?token=…` 取 HttpOnly 认证 cookie，再 `POST /api/pluginManager/listPlugins`，信封为 `{"type":"client-request","rpcId":…,"method":"pluginManager/listPlugins","payload":{"args":{}}}`（payload 必须恰好一个 plain-object `args` 字段，否则报 `gateway/internal`）。

读到的本行：

```json
{ "entryId": "include:llm-transient-retry", "moduleName": "dsh-llm-transient-retry",
  "enabled": true, "fiberPhase": "active", "patchId": "llm-transient-retry" }
```

全 profile 相位普查：187 行中 157 行 `active`、30 行 `fiberPhase` 为空且 `enabled: false`（随附 preset 行在全局层按设计禁用，不是激活失败）⇒ **不存在 enabled 却未激活的行**。平台邻居 `include:llm-retry` 同为 `active`。

判据口径说明：这里的 `fiberPhase` 是 loader 该行的运行时相位，`N entries did not activate` 对应的是「enabled 但相位非 active」，故本次普查为该门禁的机器可读等价物（`[推断]`：两者语义对应关系由文案与字段含义推定，未逐字读上游告警实现）。

layer 3 的保真依据：`Session.append` 在事件入册前派发 `session/event` 做 pre-commit 校验（`packages/core/session/src/index.ts:759-764`），上游不变量正挂在 `internal/dispatch` 的该事件上（`packages/llm/llm-retry/src/invariant.ts:162-169`）。测试的假 session 因此先派发、再入册，与平台同序；构造历史另需 `turn/start`、`step/start` 与 `request/header`，否则会被「必须在开放 turn/step 内」与 provider 一致性两条挡下。

### 9.3 真实组合验证（2026-10-14，`[实测]` 于本机）

`test/composition.test.mjs` 把一份 `cordis.yml` 交给**真 Loader** boot（`@deepseek-ai/cordis-plugin-loader`，只桩掉 `loader.internal.import` 的 specifier 解析），装配范式取自上游 `packages/llm/llm-retry/tests/loader-composition.spec.ts`（同基线 0.1.7-rc.2）；随后用真实 AgentLoop 驱动一次 turn。组合含平台 `@deepseek-ai/dsh-llm-retry` 行（真实 profile 里就在场）与其相对次序（平台在前）。

三个用例：

| 用例 | 结果 |
| --- | --- |
| 真实过载报文（`PI_AI_ERROR` + "…currently overloaded…"，provider `openai-codex`） | 重发恰好 1 次；`turn/end.reason.kind === "completed"`；写出 1 条 `llm/retry` + 1 条 `llm/retry-started`（同 `retryId`）；最终助手文本为恢复后的内容 |
| **消融**：同构造移除本插件行 | 一次都不重发；**`turn/end.reason = {kind:"error", error:{message:"Codex error: Our servers are currently overloaded. Please try again later.", code:"PI_AI_ERROR"}}`**——即 `references/Codex断连.md` 记录的原发现象，被确定性复现 |
| 同码非瞬态（`PI_AI_ERROR` + "unauthorized…"） | 不介入（1 次请求、0 条重试记录、turn 以该错误结束）⇒ 文本限定确实在起作用，不是按码放行 |

`llm/retry` 的键集合也按精确集合断言（10 个字段，不含任何自定义字段），`delayMs`/`retryId` 各自单独断言——避免自引用式断言把字段漏掉。

**接缝监听者普查（静态，`[实测]` 读运行时装好的产物）**：在 `versions/0.1.7-rc.2/node_modules/.pnpm` 全树搜 `agent/request-error`，除本插件外只有三个：

| 监听者 | 在本 profile | 对 `PI_AI_ERROR` 的行为 |
| --- | --- | --- |
| `@deepseek-ai/dsh-llm-retry` | 激活 | 按 provider 策略判定；默认 `retryableCodes` 不含 `PI_AI_ERROR` ⇒ 写不出事件、落到我方（组合测试经验证） |
| `@deepseek-ai/dsh-compaction-basic` | 全局层 `enabled:false`（preset 行） | 处理体首行即 `if (failure.code !== CONTEXT_WINDOW_EXCEEDED_CODE …) return next()` ⇒ 放行 |
| `@deepseek-ai/dsh-compaction-image-offload` | **不在行清单**（连全局层都没有） | 首行同样是别的码 `IMAGE_OFFLOAD_REQUIRED_CODE` ⇒ 纵使在场也放行 |

⇒ **没有更早的监听器会返回非 `undefined` 而不调 `next()`**，顺序假设（§11 风险 1）在本 profile 的这代运行时上不成立。注意这是**本代 + 本 profile** 的结论，不是普适性证明。

### 9.4 对先前风险评估的更正（`[实测]` + `[读码]`）

先前把「不变量拒绝 → 该 turn 报 `InvariantError`、把故障形态换了一个」列为最大残余风险。查清后**下修**：

- `@deepseek-ai/dsh-llm-retry/invariant` 是独立 plugin 模块（`name = 'llm-retry-invariant'`，`inject = ['invariants']`），但 **`bundle/base` 的 `cordis.patch.yml` 没有它的行**，test profile 的 `--dump-config` 全文也无 `invariant` 字样 ⇒ **部署组合里没有被装载**。§4 的测试因此是「包级契约合规」，不是「运行时会被拦」。
- 追加期恒在的门禁 `validateSessionEventData` 自述「**不校验完整事件载荷**」（`packages/core/session/src/surface.ts:165-176`），只查 request-header / developer 角色 / tool 失败元数据三类 ⇒ 对我方事件无 schema 校验。
- 另：我方事件用的是**平台既有**事件类型（不是自定义类型），故插件被卸下后旧会话仍可正常读取，不留孤儿事件。

⇒ 运行期的实际风险主要是「重试次数/退避不当」这类策略问题，而非「事件被拒导致错误形态改变」。

## 11. 风险与残余未知

1. **顺序假设**：已在本 profile 的这代运行时上消解（§9.3 的监听者普查 + 组合测试）——本 profile 内不存在会截胡的监听器。残余面是**换 profile / 换代的组合变化**：平台若新增一个在 `PI_AI_ERROR` 上就返回 action 的监听器，本插件会被挡在后面；这只能在部署环境再核一次（方法同 §9.3，代价是一条 rg + 读处理体首行）。
2. **故障注入点在 adapter 边界**：码与报文由夹具给定，未跑真实 `llm-pi-ai` 分类器与真实网络（分类表已按源码与参考文件的真实失败码交叉核对）。故 layer 6 仍需一次自然过载，才能把「分类器 → 本插件」整段闭合。
   - 曾尝试用已发布包把三个真实报文直接喂进分类函数，**放弃**：`classifyPiAiError` 是模块私有（源码 `stream.ts:42`），唯一公开入口 `mapStopReason`（`:80`）虽可构造入参，但该包 `exports` 里的 `./src/*` 映射指向**未随 tarball 发布**的文件，而装 `@deepseek-ai/dsh-llm-pi-ai` 会带入 **97 个包**（`@google/genai`、`protobufjs`…）。为一个边际证据给只有 1 个运行时依赖的插件塞 97 个 devDependency，不划算。
   - 该段现有证据：分类表与 `mapStopReason` 逐行读过 `[读码]`；**云端活会话里 13 次 turn 级失败全部落在 `openai-codex / PI_AI_ERROR` 且以 `turn/end.reason.kind === "error"` 收场**（§9.5，`[实测]`）——而 `agent.ts:472-491` 是「流终态错误 → turn 级失败」的唯一路径，本插件的介入点正在其间的瀑布上。
3. 第 2 句报文语义模糊，可能裹着非瞬态原因 ⇒ 以 `maxRetries=3` 封顶。
4. 用尽重试后 turn 失败 → goal 可能续跑 → 新 turn 再给 3 次；上界由 goal 轮数决定。会话级预算属过度设计，v1 不做。

## 12. 上游版本消融（附录，`[实测]` 于本机 2026-10-14）

> ⚠️ **基线更正（2026-10-14 云端实测）**：本节比对的是 `2.5.3` 与 `2.6.8` 两个 npm tarball，但云主机**实际跑的是 2.2.2**（§9.5）——2.5.3 只存在于一棵从未运行的旁路树。故本节结论只能读作「2.6.8 相对 2.5.3 的变化」，不能读作「升级能修好云端现状」；对 2.2.2 未做逐字符串比对。下面的实证补上了这一格。

拉 npm tarball 逐字符串比对 `dsh-codex-subscription`：

| 命中 | 2.5.3（旁路树，非运行态） | 2.6.8（当时最新） |
| --- | ---: | ---: |
| `retryPolicy` | 0 | 10 |
| `request buffer limit` | 0 | 1 |
| `overloaded` | 0 | 0 |

**实证补格（云端活会话，`[实测]`）**：运行中的 2.2.2 上确有 2 次 `exceeded request buffer limit while retrying upstream` 以 turn 级失败收场 ⇒ 该版本**不**自愈这一句；10 次重试记录里被重试的全是 `TRANSPORT`，`PI_AI_ERROR` 0 次 ⇒ 这一代对过载类同样不覆盖。

- 2.6.8 新增 `normalizeTransportEvent()`，把 `exceeded request buffer limit while retrying upstream` 与几种瞬态 WebSocket 关闭**改写成** `Network transport failure: …`，由 DSH 分类为 `TRANSPORT`（默认白名单）⇒ 该句升级即可自愈。已核实非死代码：挂在流的 `[Symbol.asyncIterator].next()`。
- 新增设置项 `retryPolicy ∈ {default, off, 10, 20, unlimited}`，但对过载**无效**：`retryPolicyFor()` 只传 `{mode:"normal", maxRetries:N}`、**不传 `retryableCodes`** ⇒ 仍回落默认白名单。只有 `unlimited`（`mode:"always"`）会重试，而那是无条件、无上限的。
- ⚠️ `mode:"always"` 会**静默丢弃** `retryableCodes`（`retry-policy.ts:186-191`）——「always + 白名单」这种表达无效，勿尝试。
- 配置层不可解（本机 `--dump-config-schema` 实测）：`codex-subscription` 行 config 31 个键中**没有** `retryPolicy`/`retryableCodes`/`providers`。
