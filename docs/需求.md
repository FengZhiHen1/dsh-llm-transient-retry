# 需求

## 1. 现象

在 `openai-codex / gpt-6.1-sol` 路由上，会话出现 turn 级失败：GUI 横幅为 `本轮运行失败` + `Codex error: …`，对应会话事件 `turn/end` 的 `reason.kind === "error"`、`reason.error.code === "PI_AI_ERROR"`。

转引外部扫描记录（`references/Codex断连.md`，2026-10-13，另一台 Linux 主机，13 小时内 7 次）：

| 报文 | 次数（转引，未在本机复核） |
| --- | ---: |
| `Codex error: Our servers are currently overloaded. Please try again later.` | 4 |
| `Codex error: An error occurred while processing your request. … request ID <uuid>` | 2 |
| `exceeded request buffer limit while retrying upstream` | 1 |

共同特征：`usage` 全 0（请求未产出任何 token）、自动重试 0 次（无 `llm/retry` 事件）、3 个会话中出现过连续 4 个 turn 失败。

## 2. 问题定性 `[读码]`

根因链（每一环均已在本机 0.1.7-rc.2 源码复核，见 `技术设计.md` §2）：

```
上游 SSE error 事件
  → pi-ai 包装成 CodexApiError("Codex error: " + message)      （流内错误，pi-ai 的 HTTP 重试循环已结束）
  → classifyPiAiError(text) 纯正则分类，三句均未命中 → PI_AI_ERROR
  → agent/request-error waterfall
  → llm-retry：!retryableCodes.includes("PI_AI_ERROR") → next()
  → 无其它 handler 接管 → 默认 () => undefined
  → action?.kind !== "retry" → throw new LlmError(...) → turn/end.kind = "error"
```

要点：**同一句文本，在 pi-ai 的传输层白名单里是「可重试」，在 DSH 的分类表里是「未分类」**——两侧白名单不一致，是这类失败无法自动恢复的直接原因。这不是物理断连，也不是本机网络问题。

## 3. 目标与验收标准

**目标**：这类瞬态失败在会话内自动恢复，不再升级为 turn 级失败；恢复过程对用户可见。

验收标准（缺一不算达成）：

| # | 标准 | 验证方式 |
| ---: | --- | --- |
| 1 | 三句报文在三层判据（provider ∧ code ∧ 文本）下各触发一次重试 | core 单测 + adapter 接线测试 |
| 2 | 写出的 `llm/retry` / `llm/retry-started` 通过上游**真**不变量校验器（不另写第二套实现） | 以 `@deepseek-ai/dsh-llm-retry/invariant` 为 devDependency 跑测试 |
| 3 | 重试用尽后**保留**原 `PI_AI_ERROR` 与 `turn/end.reason.error`（不吞错） | 接线测试断言抛出路径 |
| 4 | **消融可证伪**：禁用本插件行时同一构造复现 turn 级失败 | 接线测试双跑对照 |
| 5 | 非瞬态码（`AUTH`/`QUOTA_EXCEEDED`/`INVALID_REQUEST`/`CONTEXT_WINDOW_EXCEEDED`/`RATE_LIMIT`）与 `pending`/`deferred` 两种终态**不受影响** | core 单测负例 |
| 6 | 不动 `dsh-llm-retry`、不动 `dsh-codex-subscription`、无 client 半侧代码 | 代码面检查 |
| 7 | 部署纪律：`--dump-config` 按层级核对无重复行；启动无 `N entries did not activate`、无 `disabling profile plugin` | 本仓库 `knowledge/05` §6.1/§7.2 |

## 4. 非目标

- ❌ 不重试整个 `PI_AI_ERROR` 桶。该桶是「其它全部」，含认证/协议类错误；且 `stream.ts:111-118` 把 `pending`/`deferred` 两种**非瞬态**终态也归入此码。
- ❌ 不处理配额耗尽（`QUOTA_EXCEEDED` 与「You have hit your ChatGPT usage limit…」）——那是 `dsh-codex-subscription` 的既有职责，等它几十分钟重置与我们的秒级退避是两种策略。
- ❌ 不改 `classifyPiAiError()`（DSH 自身）、不让本插件成为上游缺陷的长期替代：上游一旦修正分类表，本插件**自动失效**（判据不再命中），这是刻意设计。
- ❌ 不做会话级重试预算、不做 UI 设置页、不注册模型可见工具。
- ❌ 不把「本机未复现」写成「不存在」：本机 `stable-dev` 亦装 `dsh-codex-subscription`，同样暴露在该路由下。

## 5. 覆盖范围（已拍板）

纳入：上表三句报文。
排除：其余一切 `PI_AI_ERROR` 文本，以及所有已在默认白名单内的码（`EMPTY_RESPONSE`/`RATE_LIMIT`/`SERVER`/`TIMEOUT`/`TRANSPORT`）——它们已由 `dsh-llm-retry` 处理，本插件不介入以避免双重重试。

残余风险（已接受）：第 2 句是 OpenAI 的通用错误文案，语义最模糊，可能裹着非瞬态原因；以 `maxRetries` 封顶（默认 3）作为代价上限。
